# DeepSeek Harness 实战：从 Demo 到可控成本

[English version](deepseek-harness-demo-to-controlled-cost.en.md)

> 这不是一篇“把 Agent 接上就万事大吉”的教程，而是我把一个 DeepSeek Harness Demo 逐步变成可持续个人项目时，反复踩到的三个问题：任务范围会膨胀、模型调用会变长、账单会变得难以解释。

对个人开发者来说，Harness 的魅力在于它能把模型、文件、终端命令和 MCP 工具串成一个执行循环；风险也在这里——一次看似简单的需求，可能变成几十轮工具调用和远超预期的 Token 消耗。下面是我目前采用的工作方式。

## 先把 Harness 当成“有边界的执行器”

我给 Demo 的第一个任务不会是“重构整个项目”，而是一个能明确验收的小任务，例如：

- 为一个函数补充单元测试；
- 找出某个接口的错误来源，并提出最小修复；
- 为一个 MCP 工具写出使用说明；
- 把一段重复逻辑拆成一个独立模块。

这一步看似保守，却能让我在开始阶段就测出四件事：模型是否理解代码库、工具调用是否可靠、一次任务需要多少轮、以及成本是否能接受。只有这些有了记录，我才会把任务范围扩大。

DeepSeek 目前提供 OpenAI 与 Anthropic 兼容接口，也提供与 Claude Code、OpenCode 等 Agent 工具的接入说明；但官方同样提示这些第三方 Agent 仅供参考，效果和安全性不由其保证。我的结论是：把 Harness 当作需要验证的工程组件，而不是自动交付系统。[DeepSeek API 文档](https://api-docs.deepseek.com/quick_start/pricing-details-cny/) · [Agent 接入指南](https://api-docs.deepseek.com/guides/coding_agents)

## Demo 阶段：先建立一张最小记录表

我会为每次试验记录下面五项，而不是只看“代码有没有生成”：

| 记录项 | 我关注的原因 |
|---|---|
| 任务与验收条件 | 防止 Agent 自己扩大目标 |
| 使用的模型与模式 | 区分高质量推理与低成本执行 |
| 工具调用轮数 | 很多隐性成本来自反复读文件、搜索与重试 |
| 输入 / 输出 Token | 判断成本由上下文还是生成长度驱动 |
| 人工复核后的结果 | 防止把“能运行”误当成“可以合并” |

例如，一个“为接口补测试”的 Demo，如果第一轮就能给出可运行的测试，我会先停在这里做人工检查；不会立即追加“顺便重构、补文档、改 CI”。把大需求拆成数个可验收的小回合，通常比给模型更长的自由指令更省钱。

## 从可用到可控：我加上的 6 个护栏

### 1. 为每次任务写清完成条件

我会在 Prompt 里明确文件范围、允许使用的命令、测试命令和停止条件。比如“只修改 `src/auth`，完成后运行指定测试；如果需要改公共接口，先说明原因再停下”。这既减少无关上下文，也保留了人来决定范围变化的机会。

### 2. 将昂贵推理留给关键节点

不是每一步都需要最强的推理模式。我的常见分工是：用更强的模型处理计划、复杂排错和最终审查；用更快或更经济的模型处理文件定位、简单改动和子任务。DeepSeek 的工具接入示例同样区分了主模型与子 Agent 模型配置，具体选择仍应以当前模型能力和价格为准。[Claude Code 接入示例](https://api-docs.deepseek.com/quick_start/agent_integrations/claude_code/)

### 3. 限制上下文，而不是无限追加历史

长上下文并不等于更好的任务完成率。我会让 Harness 先读取必要文件、在阶段完成后生成简短摘要，并避免把构建日志、完整依赖树和无关对话持续带入下一轮。对个人项目而言，少而准的上下文通常更容易复盘。

### 4. 限制工具权限与重试次数

只暴露当前任务需要的命令和 MCP 工具；对网络请求、写入配置、删除文件等操作保留人工确认；并设置最大工具调用次数和失败后的停止条件。这样做不只是节省 Token，也是在避免自动化把错误扩大。

### 5. 把 429、超时和失败当作正常路径

Harness 需要处理速率限制和临时故障，而不是假设每次请求都成功。我的做法是使用指数退避、限制并发、保留可恢复的任务状态，并在多次失败后切换到人工处理或备用模型。不要用无限重试来“解决”限流。

### 6. 每周只复盘一个成本指标

我会先选一个容易行动的指标，例如“每个成功任务的平均 Token”或“每个合并请求的模型花费”。如果它上升，再排查是任务变大、上下文变长，还是工具循环失控。比起盯着总消费，这种做法更容易找到真正的改进点。

## 我的模型接入选择：直接连接与统一入口

如果只验证 DeepSeek，并且所用工具需要 Anthropic 格式，我会优先对照 DeepSeek 的官方兼容文档完成最小配置。DeepSeek 的文档还特别指出，在某些工具中错误选择 OpenAI provider 可能引发与 `reasoning_content` 相关的 400 错误；协议适配并不是可以忽略的小细节。[GitHub Copilot CLI 接入说明](https://api-docs.deepseek.com/quick_start/agent_integrations/copilot_cli/)

当我想在同一个项目里比较 DeepSeek、Qwen、Kimi、GLM 等模型时，会使用 [SupaNexus](https://supanexus.ai/) 这类统一 API 入口。它提供 OpenAI 兼容端点、项目级 API Key 和模型目录，适合让我把“更换模型”控制在配置层，而不是在每个脚本里改供应商 SDK。

这不是说统一入口一定比直接 API 更好：

- **只用一个模型、依赖该厂商专有功能时**，直接 API 往往最直接；
- **需要持续比较多模型、管理多个个人项目时**，统一入口通常更省维护；
- **无论走哪条路径**，都应先核对当前可用模型、能力、限额和实时价格。

SupaNexus 目前提供免费模型试用与注册优惠；我会把它用于先完成小任务验证，再根据控制台中的可用模型与实际用量决定是否继续使用。具体试用资格和充值活动以注册后的控制台信息为准。

## 一个可复用的成本控制流程

```text
任务拆分 → 小范围 Demo → 记录 Token / 轮次 / 结果
     ↓
人工验收 → 选择合适模型 → 设置上下文与工具边界
     ↓
限流与失败处理 → 每周复盘一个指标 → 再扩大任务范围
```

这套流程没有让 Agent“无限自主”，却让我更愿意把它留在日常开发中：每次运行都有明确目标，每笔成本都能追溯，每个模型切换也有理由。

## 最后：成本可控不等于只选最便宜的模型

对我来说，真正值得优化的是“完成一个可信任务的总成本”，包括失败重试、人工返工和维护多套接入的时间。一个便宜但频繁跑偏的模型，未必比一次完成关键步骤的模型划算；同样，一个强模型也不应该被用来反复读无关文件。

从一个小 Demo 开始，记录真实数据，保留人工审查与可切换的接入路径——这比任何“全自动开发”的承诺都更适合个人开发者。
