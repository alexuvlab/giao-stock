# 我不再凭感觉换模型：用一个 API Key 做多模型 A/B 测试

[English version](one-api-key-multi-model-ab-testing.en.md)

我之前给博客的小工具换模型，做法很随意：觉得某个回答不错，就把模型名改掉；过两天遇到一次不好用的结果，又换回来。最后我根本说不清哪个模型更适合我的需求，只记得自己“好像更喜欢”其中一个。

后来我给自己定了一个很小的规矩：不再拿单个 Prompt 决定模型。每次换模型，至少拿同一批真实任务跑一遍，再把结果摊开看。

这篇不是性能榜，也不会告诉你“哪个模型最好”。它只是我给个人博客和小工具做模型 A/B 测试的一套轻量方法。

## 我先挑了 12 个真实问题

我没有去找公开 benchmark。我的工具主要做中文技术文章摘要、FAQ 改写和一点代码解释，所以测试集也就来自这些真实场景：

- 三篇长短不同的技术文章，要求写出适合博客首页的摘要；
- 两段读起来很绕的产品说明，要求改得更自然；
- 两个 API 报错，要求给出排查步骤；
- 两段 TypeScript，要求解释逻辑并指出可能的问题；
- 一组中英混合的标题和标签，要求统一格式。

我把个人信息、访问令牌和未公开内容删掉后，保存为一个小 JSONL 文件。样本不多，但至少是我真的会遇到的任务。官方 eval 指南也强调，评估集应该尽量反映实际工作流，而不是只看泛化的基准分数。[Evaluation best practices](https://developer-openai-com.sitemirror.store/api/docs/guides/evaluation-best-practices/)

## 第一次跑完，我发现“回答更长”根本不是优势

我固定 system prompt、输入、`max_tokens` 和温度，只换 `model`。然后把模型输出存下来，不看模型名，隔一段时间再人工读。

我给每条结果只记了四项：

| 我看的东西 | 我怎么判断 |
|---|---|
| 是否完成任务 | 有没有漏掉关键要求，格式能不能直接用 |
| 事实与代码风险 | 有没有编造 API 行为、把代码逻辑说反 |
| 编辑成本 | 我需要改几句才能发布或使用 |
| 速度与用量 | 等待是否影响体验，Token 有没有明显异常 |

第一个反直觉的结果是：有个模型每次都写得很完整，但博客摘要总要我删掉一半；另一个模型答案短一些，反而几乎能直接用。对我的场景来说，后者更划算——不是因为它“更强”，而是因为它少让我返工。

## 让 Prompt 和模型配置保持不变

这一步很枯燥，却帮我避免了很多自欺欺人。我以前常常一边改模型，一边又顺手改了 Prompt，最后根本不知道结果变好是哪个因素造成的。

现在我的测试调用尽量长这样：

```python
from openai import OpenAI

client = OpenAI(
    api_key="YOUR_API_KEY",
    base_url="https://api.supanexus.ai/v1",
)

def run_case(model: str, prompt: str) -> str:
    response = client.chat.completions.create(
        model=model,
        temperature=0.2,
        max_tokens=600,
        messages=[
            {"role": "system", "content": "You are a concise technical writing assistant."},
            {"role": "user", "content": prompt},
        ],
    )
    return response.choices[0].message.content
```

这里的模型 ID 需要替换成当前控制台可用的名称。真正重要的不是这段代码，而是我在一轮比较里只改 `model`；如果要测 Prompt 版本，我会单独开一轮。模型输出本身有随机性，所以也不该用一次运行就下结论。

## 为什么我会用 SupaNexus 做测试入口

一开始，我直接到不同厂商的控制台分别申请 Key。这样当然可行，但小测试越做越多，配置很快变乱：不同 SDK、不同环境变量、不同账单页面，最后连同一条请求是不是完全一致都不太确定。

后来我试着用 [SupaNexus](https://supanexus.ai/) 作为测试入口。它对我最大的帮助不是替我判断模型好坏，而是提供一个 OpenAI 兼容 Base URL、项目级 API Key 和模型目录。我可以保持调用代码不动，只改模型配置，把比较的重点留在结果上。

这也有边界：

- 如果我要验证某个厂商独有的工具、缓存或协议能力，我还是会直接接那个厂商；
- 如果某个模型没有在当前目录中可用，就不能把它硬塞进比较；
- 可用模型、价格、试用资格都会变化，测试前要以控制台信息为准。

SupaNexus 目前有免费模型试用和注册优惠。我把它当作跑小样本的起点：先确认某个模型在我的任务上是否值得继续投入，再决定是否为更大规模的调用付费，而不是先充值再寻找用途。

## 我怎么避免“自己给自己判卷”

最简单的方法是把输出里的模型名遮住，再隔几个小时看。我会先选出两个我觉得更好的答案，再回头看它们来自哪个模型。

对于能自动检查的内容，我也会加一点硬规则：JSON 能否解析、标题长度有没有超限、链接是否保留、代码块是否能通过基础检查。官方评估建议同样强调，LLM 评估应结合针对任务的检查与人工判断，而不是只看一个泛化分数。[OpenAI Evals 指南](https://platform.openai.com/docs/api-reference/evals/deleteRun?lang=python)

我不会让一个模型给另一个模型打分后就完全相信结果。它可以帮我初筛，但最后那一两条真正要上线的内容，我还是自己看。

## 测试没有给我一个“永久赢家”

同一个模型在代码解释上表现很好，不代表它适合中文改写；一个模型今天适合 FAQ，不代表下个月更新后还一样。我的测试表也因此没有“冠军”那一列，只有：

```text
任务类型 → 当前首选模型 → 备用模型 → 最近一次复测日期
```

这张表对个人项目已经够用。每当模型升级、价格变化，或者我发现用户经常修改某类输出，我就补两个样本进去再跑一次。

如果你也在不同模型之间摇摆，我建议别从“大规模评测平台”开始。挑十来个真实任务，固定输入，留下原始输出，自己读一遍。你很快会知道，自己真正需要的是更快的回答、更少的编辑，还是某种特定能力。

对我来说，一个 API Key 的意义不是把所有模型混在一起，而是让我能用同一种测试方式，慢慢找到每种任务该交给谁。
