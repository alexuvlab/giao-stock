# Agent 跑着跑着，Token 怎么就没了？

> English version: [Where Did the Tokens Go While My Agent Was Running?](../en/agent-token-usage-disappears.en.md)

前几天我看一段 Agent 运行记录：它没有写出什么像样的结果，也没完成任务，可用量却比预期掉得快得多。

一开始我还以为是模型太能想。后来把日志摊开，才发现事情没那么简单：有时是工具参数一直在生成；有时是一轮失败后，几层重试又把同一个任务跑了几遍；还有时，Agent 每走一步都带着一大段已经没用的历史。

这篇不是省 Token 的十条技巧。只是我现在看到“跑着跑着没量了”时，会先看哪几处。

## 先别急着换便宜模型

模型单价当然重要，但它只回答“每个 Token 值多少钱”。真正烧掉多少，还取决于请求有没有真的停下来。

最近 DeepSeek Harness 社区就有一个很典型的报告：本地兼容模型在生成工具参数时跑偏，参数一直流到输出上限，最后页面只剩下一句通用的 `Output token limit reached`。问题不一定在模型本身；更早地限制、截断并标记异常工具参数，至少能让人知道钱花在了哪里。[讨论原文](https://github.com/deepseek-ai/deepseek-harness/discussions/6059)

我现在会先把一次运行拆成四块看，而不是只看最终回答的 Token：

| 先看什么 | 我在找什么 |
| --- | --- |
| 输出 | 是正常回答变长，还是工具参数/思考过程没有停？ |
| 重试 | SDK、任务队列、Agent 自己是不是都在重试？ |
| 上下文 | 每一轮是否都重复带了日志、工具结果和旧话题？ |
| 统计 | 面板里的用量，是否把失败尝试和压缩请求算进去了？ |

最后这一项很容易被忽略。另一个 Harness 讨论指出，失败重试或上下文压缩的请求如果没有被正确折算，页面上的 session 用量可能比实际发出去的请求少。[讨论原文](https://github.com/deepseek-ai/deepseek-harness/discussions/2426)

## 我给 Agent 留的三个刹车

第一，工具调用也有长度上限。

以前我只给最终回答设 `max_tokens`。现在工具参数、单个工具结果和单次任务的工具轮数也会各有一个上限。不是因为每次都要卡得很死，而是我不希望一个明显不对的 JSON 或文件内容，一直把输出预算吃完。

第二，只留一层重试。

这条很笨，但很管用。一次请求失败时，我会明确谁负责重试：SDK、队列或 Agent，三者只选一个。否则看起来只是“帮忙再试一次”，实际却可能是一轮失败触发好几次调用。

第三，阶段结束就把历史收起来。

我不会把完整日志、所有工具返回和前一个话题一直塞进下一轮。能用一段小摘要代替的，就不再搬原文。缓存命中能让重复上下文便宜一些，但无关上下文不带过去才是零成本。

## 先记一行够用的日志

个人项目一开始不用做完整计费系统。我会在每次任务结束时记下这些：

```text
task=import-notes
model=...
attempts=2
tool_calls=5
input_tokens=...
output_tokens=...
result=failed_before_write
```

下次看到 Token 异常，至少能区分是某个模型变了、某类任务变大了，还是失败请求在重复跑。比起盯着一条总账单，这种记录更能帮我决定该缩短上下文、关掉某层重试，还是换模型做对照。

## 我怎么做模型对照

如果要排除模型差异，我会保持任务、工具清单和上下文都不变，只换模型跑一小批非关键样本。像 [SupaNexus](https://supanexus.ai/) 这种 OpenAI 兼容入口，对我来说方便的地方是不用把几份客户端接入代码来回改；同一套小测试可以直接比较完成率、调用轮数和用量。

它不能替我控制 Agent，也不能保证哪个模型最省。真正有用的是把“模型贵不贵”和“这次任务为什么多跑了几轮”分开看。

我现在更关心的不是某次调用用了多少 Token，而是：**这次 Token 有没有换回一个可信的完成结果。**
