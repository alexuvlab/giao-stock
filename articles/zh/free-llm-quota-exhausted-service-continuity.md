# 免费额度用完后，个人项目如何不断服务：我的 7 个保底做法

[English version](../en/free-llm-quota-exhausted-service-continuity.en.md)

> 个人项目接入 LLM API 时，我几乎都会从免费额度开始。但我后来发现，真正决定项目能不能长期运行的，不是“有没有找到免费的模型”，而是额度归零的那一刻，产品还能不能给用户一个合理的结果。

免费层非常适合做 Demo、验证需求和低频服务，却不适合被当成永远不会变化的基础设施。模型可能限流、每日配额会重置、免费模型也可能暂时不可用。下面是我给个人项目准备的 7 个保底做法。

## 1. 先承认额度会用完，并把它写进产品逻辑

我不会把“免费额度”当作一项保证，而是把它当作一种有上限的资源。比如 OpenRouter 的免费计划目前列出每天 50 次请求的限制；Cloudflare Workers AI 则提供每日 10,000 Neurons 的免费额度，并在超额时让请求失败。[OpenRouter 定价](https://openrouter.ai/pricing) · [Workers AI 定价](https://developers.cloudflare.com/workers-ai/platform/pricing/)

因此，我会为 API 调用准备至少三种结果：

- 正常完成；
- 排队稍后完成；
- 功能降级，但主流程仍可继续。

举例来说，文章摘要失败时，博客仍应保存原文；AI 问答不可用时，页面仍应显示 FAQ 或联系入口。不要让一个 LLM 调用决定整个产品是否可用。

## 2. 把“必须实时”的任务压缩到最少

很多个人项目一开始会把所有 AI 工作放在用户点击后的同步请求里：生成摘要、分类、提取标签、翻译、搜索问答一起做。免费额度一紧张，用户就会直接面对超时或报错。

我会把任务分成两类：

| 类型 | 处理方式 |
|---|---|
| 必须实时 | 只保留真正影响当前交互的一个小请求，并限制输出长度 |
| 可以稍后完成 | 进入队列，后台重试或等待下一次额度窗口 |

例如，用户提交内容后先立即保存；AI 摘要和标签生成随后异步处理。这样即使模型暂时不可用，我的核心数据和用户操作也不会丢失。

## 3. 用缓存减少“同一个问题问两遍”

对个人项目来说，缓存通常是最直接的省额度方式。我会按任务类型保存可复用结果：

- 相同输入的摘要、翻译和分类结果；
- 固定 FAQ 的问答结果；
- 文档切片、Embedding 或检索结果；
- 已经审核过的模型输出。

缓存不需要一开始就很复杂。先从“输入内容哈希 + 模型版本 + 任务类型”做 Key，就能避免刷新页面或重复提交时再次消耗 Token。注意：模型切换后应让缓存 Key 包含模型 ID，避免把旧模型答案误当作新模型结果。

## 4. 让降级路径与产品功能匹配

我的 fallback 不会只是“失败后换一个随机模型”。我会根据任务重要性准备不同层级：

1. **无模型降级**：返回模板、规则结果、旧缓存或人工内容；
2. **轻量模型降级**：用于分类、标签、简单改写等可容错任务；
3. **付费模型降级**：只用于用户明确等待、或对结果质量确实敏感的关键操作；
4. **延迟处理**：等待免费额度重置，再通过通知或任务列表交付结果。

这比在额度耗尽后反复重试更友好，也更容易控制预算。

## 5. 为付费 fallback 设置一个小而明确的预算

免费额度用完后，并不代表必须关闭服务。我更倾向于给关键功能一个很小的每日或每月预算，并为它设置硬上限：达到上限后，自动回到排队或无模型降级。

Google Gemini API 也将免费层和面向生产的付费层明确区分：免费层适合入门与小型项目，付费层提供更高限额及生产相关能力。[Gemini API 定价](https://ai.google.dev/gemini-api/docs/pricing?hl=en)

我会记录的不是笼统的“总花费”，而是：

- 每日 fallback 花费；
- 每个成功用户任务的平均 Token；
- 触发 fallback 的原因与次数；
- 哪些任务即使不用模型也能完成。

有了这些数据，才知道是该优化 Prompt、增加缓存，还是应该为某个关键功能付费。

## 6. 提前准备可切换的模型入口

如果我的项目只验证一个模型，我会直接使用对应厂商的 API，配置最简单。但当项目需要在免费试用、轻量模型和高质量模型之间切换时，我更愿意把模型接入抽象在一个地方。

这也是我会考虑 [SupaNexus](https://supanexus.ai/) 的原因：它提供 OpenAI 兼容端点、项目级 API Key 和模型目录。对个人项目而言，它的实际价值不是“保证永远免费”，而是让我把模型选择和 fallback 放在配置层，不必为每个供应商反复改 SDK 与业务代码。

SupaNexus 目前提供免费模型试用与注册优惠。我会先通过试用验证任务效果，再根据控制台里的可用模型、实时价格和自己的预算决定是否继续使用；试用资格、活动与充值优惠均应以注册后的控制台为准。

## 7. 把额度耗尽当作一次可观测的事件

最后，我会为每次 API 失败记录：时间、模型、错误码、请求类型、估算 Token 和降级结果。这样“免费额度为什么突然没了”不会只是一句模糊抱怨，而能变成下一次优化的依据。

一个最小告警规则就足够开始：

```text
若免费额度剩余不足 20%：减少非关键后台任务
若收到 429 / quota error：暂停同类请求并进入队列
若 fallback 预算达到上限：切换为缓存、模板或人工处理
```

不要用创建多个账号、无限重试或隐瞒错误来对抗免费层限制。这些做法不可持续，也会让项目在真正有用户时更脆弱。

## 我的结论：免费是起点，连续服务才是目标

免费额度让我低成本验证了很多想法，但让我敢把项目交给用户的，是缓存、队列、功能降级、预算上限和多模型 fallback。

如果项目的核心体验不依赖“每一秒都必须得到模型回答”，那么额度耗尽并不需要变成停服。先保住用户操作和数据，再选择排队、缓存、轻量处理或受控付费——这才是个人开发者能长期维护的 AI 产品节奏。
