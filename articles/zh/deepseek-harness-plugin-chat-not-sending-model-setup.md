# DeepSeek Harness 插件装好了，但聊天框还是发不出去：我的模型配置排查

[English version](../en/deepseek-harness-plugin-chat-not-sending-model-setup.en.md)

我本来以为这会是一件很快的事。

先启动 DeepSeek Harness，再装一个模型选择插件，打开网页，应该就可以开始试模型了。插件确实装上了，DSH 也确实跑起来了；可页面最开始的状态却很诚实：聊天框不能发，模型列表也没有可以选的东西。

不是插件坏了。是我把“插件已经安装”和“这个环境已经能调用模型”当成了一件事。

这篇记的是我这次从安装到定位问题的过程。它不是一份凭空复制 API Key 的教程，也不假装所有 OpenAI 兼容服务只填一行地址就能跑通。

## 插件安装成功，到底意味着什么？

我装的是 SupaNexus 团队维护的 [`dsh-plugin-chat-enhance`](https://github.com/supanexus/dsh-plugin-chat-enhance)。它给 DeepSeek Harness 补了几项我很想要的界面能力：搜索模型、最近使用的模型、图片能力标签和输入栏上传图片。

安装命令本身很短：

```bash
dsh plugin --profile web add github:supanexus/dsh-plugin-chat-enhance#v0.3.0
```

安装完成后，我用 DSH 的配置输出确认插件已在 Web profile 中加载，能看到它自己的配置项：

```yaml
id: supanexus-chat-enhance
name: '@supanexus/dsh-plugin-chat-enhance'
config:
  maxRecent: 4
```

到这里，“插件没装上”已经可以排除。但这只证明 UI 扩展进入了 DSH，并不等于某个模型提供方已经有凭据、可用模型和正确的调用地址。

这个区别很重要。模型选择器可以让长列表更好用，却不能替我创建 API Key，也不能凭空知道某个网关允许哪些模型。

## 第一个卡点：首次启动没有模型凭据

DSH 的首次启动页会要求添加 API Key。默认页面给出的是 DeepSeek 官方提供方；如果此处没有保存可用 Key，应用仍可以打开，但无法真正把一条消息交给模型。

我没有把 Key 粘进终端命令、项目 `.env`、截图或文章草稿。更安全的路径是直接在 DSH 的 **设置 → 模型** 页面填写，并让它保存在 DSH 自己的本地凭据配置里。

这里我给自己留了一条简单规则：

```text
插件仓库可以公开
模型名称可以公开
Base URL 通常可以公开
API Key 永远不进代码、日志、截图或 GitHub
```

这看起来像常识，但第一次为了“快点看到界面”时，最容易把测试 Key 贴到不该贴的地方。

## 第二个卡点：插件、提供方和模型目录是三层

后来我把界面拆成三层来理解，排查就没有那么乱了：

| 层 | 负责什么 | 出问题时的现象 |
| --- | --- | --- |
| DSH 插件 | 搜索、最近模型、图片标签、上传入口 | 功能按钮或选择器不出现 |
| 模型提供方 | API 协议、Base URL、API Key | 不能拉取模型，或请求认证失败 |
| 模型目录 | 哪些模型能在选择器中显示 | 选择器为空，或只能手动填写模型 ID |

我之前的误判在于：插件页面看起来正常，就以为下面两层也已经准备好。实际上它们互不替代。

比如，`dsh-plugin-chat-enhance` 的 README 已经说得很清楚：模型的搜索和切换不依赖 SupaNexus Core；但图片标签和上传需要当前模型明确声明支持图片输入。也就是说，界面不会把“能上传文件”偷换成“模型一定能看图”。

## 第三个卡点：聊天框禁用不一定是模型报错

我遇到的另一个容易误会的状态，是聊天框直接不可发送。页面提示我先选择工作区。

这和 API Key 是否有效是另一回事。DSH 的 Web 界面需要先有一个会话工作区，输入框才会进入可用状态；模型配置决定的是它能不能在发送后得到回答。

所以我现在不再看到“发不出去”就只盯着 API：

```text
[ ] 是否已选择工作区？
[ ] 是否已创建或打开会话？
[ ] 是否已保存模型提供方凭据？
[ ] 提供方的 API 协议和 Base URL 是否匹配？
[ ] 模型是否出现在目录中，或能明确指定模型 ID？
```

按这个顺序看，能把界面状态问题和网络/认证问题分开。它比不断重装插件有效得多。

## 如果要接 OpenAI 兼容提供方，我会先核对三项

DSH 的“添加自定义提供方”表单要求 Provider ID、显示名称、API 地址、协议和 API Key。对 OpenAI 兼容接口，页面里可以选择 `openai-completions`、`openai-responses` 或 `anthropic-messages`；这不是随便选一个都一样。

我会先从服务商控制台或 API 文档确认：

1. Base URL 是否已包含 `/v1`；
2. 实际端点对应的是 Chat Completions 还是 Responses；
3. 模型目录是否能获取，或需要自己添加模型 ID。

我也会把 [SupaNexus](https://supanexus.ai/) 放在这个“自定义提供方”场景里看：它是我用来尝试多模型 OpenAI 兼容调用的一个入口，不是 DSH 插件的强制依赖。实际 Base URL、可用模型、图片能力和试用资格都应以登录后的控制台为准。

## 我最后得到的不是一份神秘配置，而是排查顺序

这次没有遇到很戏剧化的 bug。插件安装是成功的；真正缺的是能让会话跑起来的模型配置，以及一个已选定的工作区。

下次再装 DSH 插件，我会先做一条最小验证，而不是看到界面就开始比较模型：

```text
1. 安装插件并重启 DSH Web
2. 确认插件出现在设置/配置中
3. 选择工作区并新建测试会话
4. 在设置里保存一个可用提供方
5. 用无敏感内容的短消息验证一次调用
6. 最后才测试搜索、最近模型和图片上传
```

这条顺序不炫，但足够让我知道哪一层真的没有准备好。
