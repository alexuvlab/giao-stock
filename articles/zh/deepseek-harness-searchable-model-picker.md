# DeepSeek Harness 里的模型越来越多：我为什么先装了一个可搜索的模型选择器

[English version](../en/deepseek-harness-searchable-model-picker.en.md)

我最近打开 DeepSeek Harness 时，真正拖慢我的不是模型回答，而是选模型。

模型名单一长，事情就开始变得很笨：上次那个适合改代码的模型叫什么？能看图的是哪几个？同一个提供方是不是有两个名字很像的版本？我不想每次都靠记忆翻下拉框，更不想为了“试一下”来回打开控制台。

所以我先留意到了 SupaNexus 团队刚开源的 [`dsh-plugin-chat-enhance`](https://github.com/supanexus/dsh-plugin-chat-enhance)。它不是另一个聊天壳，也不试图替代 DeepSeek Harness；它只把我每天都会碰到的模型选择和图片输入这段界面补得更顺手一点。

这篇是我为个人工作流做的安装前笔记，基于该仓库当前 `v0.3.0` 的 README 和公开实现说明整理，不是性能测评，也不假装已经在生产环境跑了很久。

## 我不想再背模型名

个人项目的模型选择往往不是“固定用一个最强的”这么简单。

我会把较便宜的模型留给整理文本、生成草稿和重复任务；需要更稳的推理或代码修改时换另一类模型；偶尔还要判断当前任务是否需要图片输入。问题不在于没有选择，而在于选择一多，切换成本会悄悄高到让我懒得比较。

这个插件处理的是几个很小、但确实高频的动作：

- 在模型选择区按名称搜索；
- 按提供方筛选，不必在一长串模型里肉眼找；
- 把最近用过的模型显示成快捷入口；
- 给声明支持图片输入的模型标一个“图片”标签；
- 在输入框旁提供图片上传入口。

这些功能没有让模型突然变聪明，但它们让“选对当前任务的模型”更接近一个两秒钟能完成的动作。

## 我会先把它装在 Web profile 上

仓库给出的安装命令很直接：

```bash
dsh plugin --profile web add github:supanexus/dsh-plugin-chat-enhance#v0.3.0
```

安装后需要**完全重启** dsh web 或 Desktop Host，并用启动时打印出的带 `?token=` 的地址重新打开。这个步骤值得写下来：插件类问题里，最常见的“装了但没出现”，往往不是功能坏了，而是旧的 Web 页面还在运行。

我通常会在安装前先记住当前正常工作的模型和一个简单对话，重启后只验证三件事：模型选择器能不能搜索、最近模型有没有出现、原本的发送流程有没有受到影响。先确认基础路径，再去碰图片上传或筛选规则，排错会轻松很多。

## 一个更适合个人项目的切换习惯

我不会把模型列表当成“排行榜”。更实用的做法是给常见任务留三个入口：

| 场景 | 我先看的能力 | 选择动作 |
| --- | --- | --- |
| 写草稿、整理资料 | 成本、速度、上下文长度 | 从最近模型直接切换 |
| 改代码、排查问题 | 代码表现、工具调用稳定性 | 搜索具体模型名 |
| 截图、图表、界面问题 | 是否明确支持图片输入 | 打开“仅图片”筛选 |

这也是我喜欢“可搜索 + 最近使用”组合的原因。搜索负责处理偶尔才用的模型；最近模型负责保留我已经验证过的几个工作选项。它避免了把所有选择都塞进同一份心智清单里。

插件的 `maxRecent` 默认值是 `4`，可在配置或插件设置里调整：

```yaml
config:
  maxRecent: 4
```

对我来说四个就够了。太多快捷入口又会把问题变回“该点哪一个”。

## “图片”标签不是魔法开关

这里有一个细节我觉得挺好：插件没有把图片上传假装成所有模型都能用的能力。

README 说明，模型选择搜索和切换不依赖 SupaNexus Core；但图片标签和上传功能需要当前模型已经声明支持图片输入。如果没有这份能力声明，对应功能保持不可用，而不是把图片发出去再让用户猜失败原因。

这正好符合我的使用习惯：先问“这条调用链有没有能力”，再问“我要不要把图片交出去”。

我平时把 [SupaNexus](https://supanexus.ai/) 当作多模型试验入口之一，主要是为了在兼容的调用方式下做小样本对比。它不是这个插件的前置条件，也不代表每个模型都天然支持图片。实际可选模型、能力标识、试用资格和价格仍应以登录后的控制台为准；涉及敏感图片时，也应该先确认自己接受对应模型和服务的处理边界。

## 我会先用一个低风险场景验证它

插件的第一轮使用，我不会拿客户截图或带密钥的项目目录测试。

一个更合适的验证方式是：新建测试会话，上传一张公开的界面截图，选一个已经明确标注“图片”的模型，请它列出三个界面问题。然后再换一个非图片模型，确认界面确实不会把上传能力错误地开放出来。

这样能同时检查三件事：模型筛选是否准确、图片草稿是否正常加入会话、失败时的边界是否清楚。任何一个环节不对，都比在真实任务中才发现要便宜得多。

## 这类小插件为什么值得装

DeepSeek Harness 本身解决的是对话和工作流的基础问题。个人使用久了之后，摩擦常常不在“大功能缺失”，而在几十次重复的小动作：找模型、回忆上次用的版本、确认它能不能看图。

`dsh-plugin-chat-enhance` 的目标很克制：让这些动作少一点来回。对我来说，这比再加一层“自动帮我决定一切”的抽象更有用——模型仍然由我选，但界面不再要求我记住所有细节。

如果你也在 DeepSeek Harness 里频繁切换模型，可以从仓库的安装说明开始：[`supanexus/dsh-plugin-chat-enhance`](https://github.com/supanexus/dsh-plugin-chat-enhance)。我下一步会实际跑一轮公开样例；等有了真实的使用记录，再补充哪些筛选和图片能力在我的环境里最有价值。
