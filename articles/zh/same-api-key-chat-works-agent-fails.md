# 同一个 API Key，为什么聊天能用，Agent 却不工作？

[English version](../en/same-api-key-chat-works-agent-fails.en.md)

我最近在给一个本地工具接模型时，先做了最简单的验证：填入 API Key，发一句“你好”，拿到了正常回复。那一刻很容易以为接入已经完成了。

后来把同一套配置交给 Agent 跑，情况就不一样了。它可能停在模型列表、流式输出，或者第一次工具调用的地方。聊天窗口能回答问题，只能说明最短的一条路径是通的；Agent 走的是另一条路。

这不是某一个提供商独有的问题。只要一个工具开始同时涉及模型发现、请求格式、流式响应和工具调用，"能聊天" 就不再是一个很有代表性的验收条件。

## 先别急着换 Key

我一开始最想做的，是换一把 Key 再试一次。后来发现这通常只是把排查变得更乱。

先把问题拆开更有效：

1. 工具是否能拿到模型列表；
2. 选中的模型名是否真的是聊天模型；
3. 普通非流式对话能否返回；
4. 流式响应是否能一直保持；
5. 工具调用的请求和返回格式是否被该模型支持。

这五步里，前两步出问题时，常见表现是“界面看起来已经配好了，但 Agent 没有可用模型”。后三步出问题时，聊天可能仍然正常，直到 Agent 真正准备调用工具才暴露出来。

## 模型列表不是一个装饰

很多 OpenAI-compatible 接口都能接受一段聊天请求，但并不代表客户端能用同样的方式发现模型。工具有时会读取 `/models`，再用其中的 ID 决定能力、下拉选项或默认路由。

所以我现在会把“能看见预期模型名”当成独立检查项。不要根据网页里展示的模型名称手动猜一个 ID，也不要把某个推理、图像或嵌入模型当成聊天模型塞进去。名字相近不等于协议和能力相同。

## Agent 比聊天多了几层约定

一次普通聊天，大致只需要把消息发出去并读回文本。Agent 还要处理工具定义、工具参数、工具结果、下一轮上下文，以及经常被忽略的流式事件。

这里最容易误判的是工具调用：模型可以输出一段看起来像 JSON 的文字，但客户端期待的也许是特定字段中的结构化 tool call。前者在聊天窗口里看不出问题，后者才决定 Agent 能不能继续。

我的做法是先用一个只读、参数很少的工具测试，例如读取当前目录或列出一个小集合。不要一上来就让 Agent 写文件、发请求或改数据。这样即使失败，也容易看清究竟是模型、网关，还是工具本身的权限边界出了问题。

## 同一个入口不等于所有模型都一样

这次排查时，我用过一个 OpenAI-compatible 聚合入口（SupaNexus）来切换不同模型做对照。它帮我把“接口连不上”和“当前模型不适合这条 Agent 路径”分成了两件事；但它并没有替我省掉兼容性检查。

同一个 API Key 下的不同模型，可能在工具调用、上下文长度、流式行为和限流策略上完全不同。对个人项目来说，把模型名和能力假设写在一处配置里，比散落在业务代码里好得多。出问题时，至少知道该从哪里改，也能换一个模型做最小对照。

## 我现在怎样判断“接好了”

我不再只看聊天框有没有一句回复，而是留下一个很短的检查清单：

- 模型列表里有目标 ID；
- 普通对话和流式对话都能完成；
- 一个只读工具能被正确调用并返回结果；
- 失败时日志里能区分认证、限流、模型能力和参数格式；
- Key 没有出现在仓库、截图或调试日志里。

这套检查没有多酷，但它比在“聊天明明能用，为什么 Agent 不动”的状态里反复换配置省时间得多。接入完成不是看到第一句回复，而是工具链按预期走完一遍。

---

*这是一篇个人开发笔记，不构成任何服务或模型的兼容性承诺。不同客户端、模型版本和配置的行为可能不同。*
