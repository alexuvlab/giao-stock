# 工具一多，Agent 就开始乱选

> English version: [Too Many Tools, and the Agent Starts Picking at Random.](../en/too-many-tools-agent-selection.en.md)

前几天我在一个带工具调用的小流程里，碰到一个很烦的现象。

同样的提示词、同样的模型，前两天还会选对工具，后来却开始在几个名字相近的操作之间摇摆。有时它会先查一遍正确的数据，再调用一个几乎同名、但作用稍有不同的工具。输出看起来还挺合理，所以一开始我以为是模型状态不稳定。

后来才发现，问题没那么玄。是我给它看的工具太多了。

## 工具多不是问题，全部放进同一轮才是

接口一多，很容易顺手把所有能力都暴露出去。毕竟每个工具都有 schema，模型理论上可以自己选；少写一点路由代码，听起来也挺省事。

但真实的列表不会像 demo 那样干净。`search_user`、`find_user`、`get_user`，再加上不同权限下的更新、归档、导出操作，模型要先从一堆相似描述里猜出自己该看哪一个。工具本身没错，模型也没有突然变笨，只是它的工作台已经有点挤了。

MCP 的工具规范允许服务端提供随授权变化、也会动态更新的工具列表；它并没有要求把整个能力目录都塞给模型。[官方工具规范](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) 里还特别提到，稳定的工具排序有利于客户端缓存和提示词缓存命中。

## 我现在先让它看“目录”，再给工具

我的做法没有很复杂。

先给每组 API 操作留一张很短的卡片：它属于哪个服务、做什么、是读还是写、有没有风险。模型先根据当前任务从这些卡片里找少数候选；真正带完整参数 schema 的工具，只在下一步给出来。

这一步看着像多绕了一层，实际排查时反而轻松很多。工具选错了，我先看候选有没有选对；参数不对，再看具体工具 schema。两件事终于不再混在一起。

写操作我会更保守一些。查资料可以给三四个候选，创建、修改、删除这种操作通常只放一个明确的选项，并保留确认步骤。模型不该因为看到了十种写法，就获得十种尝试的机会。

## 统一模型入口，和缩短工具列表，是两回事

我用 [SupaNexus](https://supanexus.ai/) 做不同 OpenAI 兼容模型的测试入口时，确实能少改一些模型接入代码。但它解决的是“这次用哪个模型”的问题，不会自动解决“模型这一轮应该看到哪些工具”。

这两个边界分开以后，测试也更诚实了：换模型时，工具候选集不变；调整工具目录时，模型端点不变。哪怕某个模型突然表现差一点，我也不会立刻把锅全推给它。

## 最后删掉的不是能力，是噪音

我没有把 API 功能删掉，只是不再让它们全部挤进一次调用里。真正需要时，模型还是可以先搜索、再拿到合适的工具；只是不会在每一道题前先看到整本说明书。

现在遇到工具调用变差，我会先问一个很朴素的问题：它是不是根本不需要看到这么多东西？

多数时候，答案比换一个更大的模型便宜。
