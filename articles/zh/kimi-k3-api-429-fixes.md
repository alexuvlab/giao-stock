# Kimi K3 API 429 怎么办？我用这 6 步让个人项目不再卡住

[English version](../en/kimi-k3-api-429-fixes.en.md)

> 我第一次在个人项目里遇到 Kimi K3 的 `429`，直觉是“模型不稳定”。后来排查才发现，429 不是一个单一问题：它可能是请求过快、并发过高、额度窗口耗尽，也可能是服务端短时过载。把它们混在一起重试，只会让问题和成本更糟。

这篇记录的是我处理 Kimi K3 API 429 的个人开发者工作流。它不是“无限使用 Kimi K3”的技巧，也不承诺绕过任何平台限制；目标是让一个小项目在遇到限流时能清楚地判断、优雅地降级和恢复。

## 先确认：429 具体在说什么？

Kimi 官方把 429 归为速率限制或额度问题，并建议控制请求频率、实施指数退避、使用队列，以及在需要时提高限额。API 限额按用户而不是 API Key 维度执行，且不同模型可共享限额；因此，单纯多建几个 Key 并不能从根本上解决问题。[Kimi API 概念说明](https://platform.kimi.ai/docs/introduction) · [Kimi API 常见问题](https://www.kimi.com/en/help/kimi-api/api-troubleshooting)

我会先从日志里判断属于哪一类：

| 现象 | 我会先做什么 |
|---|---|
| 短时出现、稍后恢复 | 采用有限次数的退避重试，并降低并发 |
| 连续 429、集中发生在同一账户 | 检查 RPM / TPM、队列和账户当前限额 |
| 刚充值仍报错 | 确认使用的 API Key 是否属于正确账户，再核对生效时间与限额层级 |
| 多轮 Agent 任务突然失败 | 检查是否有默认 SDK 重试、子任务并发或上下文膨胀 |

不要把 429 当成“再发一次总会成功”。先分型，才能选择正确的恢复动作。

## 第 1 步：给重试加退避、抖动和上限

对可重试的临时 429，我使用有限次数的指数退避：等待时间逐步增加，并加入少量随机抖动，避免多个失败请求在同一秒再次撞到限额。超过最大尝试次数后，任务应进入队列或返回一个清晰的“稍后重试”状态。

```python
import random
import time

def wait_before_retry(attempt: int) -> None:
    # 1s、2s、4s、8s；加一点抖动，最多等待 30 秒
    delay = min(2 ** attempt, 30) + random.uniform(0, 0.5)
    time.sleep(delay)
```

这段代码不是完整客户端，只说明原则：**退避应该有终点**。无限重试既会拖住 Worker，也可能在配额恢复前持续放大请求数。

## 第 2 步：检查 SDK 的默认重试

这是我最容易忽略的一点。Kimi 文档提示，一些 OpenAI SDK 在连接错误、408、409、429 和 5xx 时默认会重试两次；一次看似失败的业务操作，可能已经变成两到三次 API 请求，并都计入 RPM。

所以我会先检查客户端日志与配置，再决定由 SDK 还是由应用层负责重试。对于 Agent、队列消费者或并发任务，最好只保留一个明确的重试层；否则每一层都“好心重试”，最终会彼此放大。

## 第 3 步：把并发变成一个可观测的队列

个人项目最常见的问题不是单次调用，而是同时启动多个任务：网页请求、后台摘要、定时任务和 Agent 子任务一起跑。我的处理方式是将调用放进一个队列，并为每个模型设置保守的并发上限。

最开始可以只记录三个数：

- 队列等待时间；
- 每分钟发出的请求数；
- 429 次数与发生时间。

如果 429 集中发生在某个批处理任务，就先降低该任务的并发，而不是马上把所有请求都切走。排队会让响应变慢，但通常比失败后反复重跑更可预测。

## 第 4 步：缩短不必要的上下文与输出

对于长任务，我会使用流式输出，并限制 `max_completion_tokens`、文件范围和工具调用轮数。Kimi 文档也建议在长生成场景启用流式输出，以降低中间网关因等待过久而中断连接的概率。

这里的重点不是一味压缩上下文，而是移除没有帮助的内容：重复日志、已完成阶段的完整对话、无关文件和过多的工具描述。更短、更聚焦的请求往往既降低成本，也降低触发限额的概率。

## 第 5 步：为 Agent 任务设置停止条件

如果一个 Agent 能无限读文件、调用工具和派生子任务，429 只是迟早会出现的结果。我现在会为每个任务写下：

- 可修改的目录和允许使用的工具；
- 最大工具调用轮数；
- 何时需要人工确认；
- 连续失败后是暂停、入队还是切换为人工处理。

这也是为什么我不会把“自动重试成功”当作唯一指标：如果任务范围本身不受控制，即使暂时避开 429，成本和风险仍然会累积。

## 第 6 步：准备明确、诚实的 fallback

当需求确实不能等待时，我会准备两类 fallback：

1. **任务降级**：将非关键任务延迟处理，或使用更短上下文与更轻量的流程；
2. **模型降级**：将经过验证的通用任务切换到另一个适合该任务的模型，而不是假装 Kimi K3 仍然可用。

在我需要比较或切换 DeepSeek、Qwen、Kimi、GLM 等模型的个人项目里，[SupaNexus](https://supanexus.ai/) 是我会考虑的统一 API 入口。它提供 OpenAI 兼容端点、项目级 API Key 与模型目录，使模型 fallback 可以停留在配置层。

这不意味着 SupaNexus 能绕过 Kimi 的官方限额，也不应该把它描述成“不限流”方案。它的价值在于：当一个模型暂不可用或不适合当前任务时，我可以使用已验证的其他模型路线，而不必在每个项目里重新接入一套供应商 SDK。SupaNexus 目前也提供免费模型试用与注册优惠；具体可用模型、试用资格和活动规则应以注册后的控制台为准。

## 我的最小排障清单

遇到 429 时，我会按下面顺序执行：

```text
确认错误体和时间点
    ↓
检查 SDK 默认重试与实际请求数
    ↓
限制并发，启用队列与指数退避
    ↓
缩短上下文，限制 Agent 工具轮数
    ↓
核对当前账户限额、余额和 API Key
    ↓
必要时延迟任务或切换已验证的 fallback 模型
```

## 最后：别把“没有 429”当成唯一目标

429 不是一定要被消灭的错误，它是在提醒我：当前请求节奏超过了某一层能力边界。一个可靠的个人项目不该靠疯狂重试支撑，而应当能告诉用户正在等待、能恢复未完成任务、也能在适当的时候换一条模型路径。

当我把限流当作正常工程约束，而不是平台“坏掉了”，Kimi K3 才真正变成一个可管理的开发工具。
